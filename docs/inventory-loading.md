# Inventory loading

## First display and session cache

The first Inventory request displays 50 matching rows and bundles the next two pages in that same response. Pages 2 and 3 enter the browser cache before page 1 appears, so they do not wait for the full background download or another server request. Each page is cached separately on the server and assembled into the initial bundle; only 50 rows are rendered at a time. The response also includes counts for the full filtered inventory and the first page of its three summary dialogs. Active and On Sale start checked, with Inactive unchecked. Filtering and sorting become local after the compact download; text searches become local after detail preparation completes, so partial downloads never produce incomplete search results.

After sign-in or restoration of a saved session on reload, the browser requests the first 50 matching rows, even when another page is open. An existing request for that same query is reused. Only after this first response renders does the browser start downloading all compact inventory records sequentially in batches of up to 1,000. This prevents the first page and background download from rebuilding the same cold server index concurrently. Manager-report and transaction-history warmups start after the first page renders; restoring a non-cashier page does not also fetch the hidden cashier catalog. Opening Inventory reuses the prepared page, current request or completed dataset.

A cached first page returns immediately with whichever priority pages remain cached. Losing a page 2 or 3 cache entry no longer forces a complete index rebuild before page 1 can return; the background download supplies the remaining data. Cold reads still prepare the first three pages together. The small **Preparing inventory…** indicator shows progress without blocking the displayed page. Records include inactive items so changing the status selections works locally later. This first pass downloads table data. Once it completes, a second background pass preloads item details, including permitted costs, original prices and delivery information. Thumbnail URLs are cached as data; actual images load lazily when visible. Item history and generated reports remain on demand.

The compact download fetches all non-inactive records first, then inactive records. An item is inactive when Inventory marks it INACTIVE or its product status is DEACTIVATED. Once the first segment completes, default Active/On Sale tables and summaries can use that segment locally while **Preparing inactive inventory…** runs. Queries that could include inactive records, and searches awaiting item details, continue using complete server results until the full dataset is ready. Inactive records append to the same revision before item-detail and Delivery preparation begin. Older callers that omit the segment still receive the full snapshot. Neither stage changes stored statuses or data.

The completed dataset is retained in memory for the current login/tab session. It has no timed browser expiry. Category/status/exclusion filters, sorting, pagination and summary dialogs use this dataset, rendering at most 50 rows at once. After details preload, text search also uses this dataset. Only four recent filtered/sorted views are retained alongside the dataset to avoid accumulating every possible query. Hard browser reload starts a fresh download; logout clears the dataset and in-flight work before another account signs in.

After inventory detail preparation finishes, the browser preloads the Delivery page and its bundled summary into the existing account-scoped session cache without navigating away. Delivery requests already pending or cached are reused. Opening Delivery uses the prepared data; existing mutation invalidation and failed-read retry behavior remain unchanged.

The previous filter-choice and next-page preloading queues were replaced by this single full-dataset download. Browser and server use the same explicitly exported pure query/display functions. No authentication, supplier-cost readers or sheet-access functions are exported to the browser.

## Refresh and consistency

Inventory data revisions change after sales, reservations, deliveries, returns, inventory edits and relevant manual sheet edits handled by installed automation. Production-to-Dev sync invalidates the Dev revision separately. The revision no longer contains a time bucket: expiration of the server's five-minute performance cache does not expire a completed browser dataset.

Existing account-session checks also return the current inventory revision, without scanning Inventory. The browser checks in the background periodically, on focus and when returning to Inventory. Normal saves return an `inventoryPatch` covering changes since the browser's cached revision. It contains complete, role-filtered affected items and deleted codes. The browser replaces, inserts or removes those records, retains unrelated item details, and recalculates summaries, filters, sorting and sale-price rows locally. Inventory modal save callbacks no longer force a full refresh. An open detail view updates only if its item changed.

Stock movement logging records affected barcodes in the current request. Direct product edits, status changes, deletes and reservation status changes also identify their items. Beginning and finishing a mutation publish a revision and a best-effort server-cache change record. For another account's changes, the browser requests `getInventoryChanges` and applies the same item updates. The change chain lasts up to one hour, is followed for at most 32 committed revisions, and is limited to 1,000 distinct affected codes. The endpoint reads a barcode column and groups affected rows into bounded contiguous ranges; it does not rebuild the complete list index. Full item costs remain server-filtered for the authenticated role.

Unknown manual/import/sync changes, an evicted change record, overlapping writers, failed or incomplete writes, too many changes, and duplicate affected barcodes require a full-refresh fallback. A mutation in progress is retried quietly; an abandoned marker falls back after two minutes. While refreshing a completed cache, its previous snapshot remains usable with a **Refreshing inventory…** indicator; the replacement is swapped in only after all batches complete for one revision. A change during initial preparation still restarts against one consistent revision. Repeated changes or a network error pause preparation and provide Retry.

The app and installed edit automation must invalidate the revision for writes. An external import or script that bypasses both must call `invalidateInventoryRead_()`; there is deliberately no timed browser reset to compensate for untracked external writes.

Display caches never authorize stock changes, payments or manager permissions. Checkout and edits still validate authoritative sheet data; all item, change and cost reads validate the current authenticated account and filter costs by role. Until detected changes arrive, the existing snapshot may briefly display older values. Change records contain barcodes and revision links, not credentials or cost values.

## Inventory actions

Add Product generates a six-digit candidate code immediately in the browser, checking cached inventory, loaded Product Master entries and codes already issued in the tab. The save still runs under the server lock and rejects conflicts in Product Master or Inventory before creating records. A rare cross-account collision requires reopening Add Product for another code; an existing product is never silently overwritten. The compatibility server generator reads only the two barcode columns, and new-product save no longer loads full inventory just to detect an existing code.

Wholesale is a STOCK product category available in Add/Edit Product, inventory and Product Master filters, summary cards, dashboard category breakdown and YourStyle Direct receiving. Category values use `WHOLESALE`; legacy `WHOLE SALE` values normalize on reads without rewriting historical rows. Stock movements retain the existing OTHERS movement type. When a target category cell has an existing list/range validation, Wholesale is appended to its permitted choices. Wholesale receiving uses Direct mode; existing PINS/OTHERS bundle processing is unchanged. Incremental cache updates normalize category keys consistently with the initial inventory dataset.

Edit opens its modal immediately with a loading indicator. Fields stay hidden and inert until complete item details arrive, so missing costs or original prices cannot be saved as blanks. Closing the modal or opening another item prevents a late response from reopening it. View immediately shows the selected name and photo while loading remaining details.

After the compact inventory download, missing valid item details preload sequentially in batches of up to 200 barcodes. Each batch groups reads into bounded contiguous inventory ranges, reuses Product Master and legacy delivery metadata caches, and reads custom costs in one range when authorized. Already cached details are skipped. Costs are attached only for manager-view roles on the server. Duplicate barcodes are excluded from this cache so opening them still fails the authoritative single-item lookup. Preparation progress appears without blocking other pages; completion clears the indicator. A failed batch retries twice, then leaves already cached details usable and falls back to an on-demand read for missing items.

All preloaded detail records stay in memory for the current account and inventory revision; the previous 100-item cap and 15-second expiry are removed. View and Edit use these records synchronously once preparation finishes. A complete incremental patch promotes unrelated cached details to the new revision and replaces only affected records. Pending reads for affected items are cancelled and resolve from their updated cache; unrelated pending reads remain usable. If detail preparation was incomplete, it resumes with only missing records. Full-refresh fallback and logout still cancel pending batches and clear details, preventing late responses from another revision or account from repopulating them. Repeated single-item server reads also use a five-minute revision-keyed cache, with separate entries for manager and non-manager responses so cost information is never shared with non-manager reads. Once the full inventory dataset is ready, Change Item builds its choices locally instead of requesting the same products again. Save and stock-change authorization remain unchanged.

Stock Adjustment and Change Item show a spinner and **Processing…** immediately after confirmation. Their controls, Cancel and close buttons are disabled during processing; a pending-action guard rejects repeat submissions. Failed or cancelled approval restores the form without clearing entered values. Account resets release any pending UI state.

These stock actions use live barcode and target-row reads rather than calling `getFullInventory()` to locate each affected item. Change Item resolves both rows under its existing lock and uses the stock values from that read, removing two redundant cell reads. Manager approval, stock checks, movement logging and rollback remain in place. This reduces work on the save path; live processing times have not been measured.

Change Item validates both movement rows before writing them together with one `setValues()` call under the existing lock. Approval-required actions reuse their freshly validated before-state for the audit record instead of reading it again. Successful stock adjustments and item changes can reuse cached product definitions and delivery metadata across their revision change, since those actions do not alter that metadata. Reuse is skipped after overlapping or unknown changes and retains the original cache age, so repeated adjustments do not extend its lifetime. Authorization, live stock validation, audit completion and rollback remain synchronous.

## YourFinds label picker

Reprint YourFinds Labels derives its list from the completed inventory/detail session cache, without a server request. Browser and server share the same pure eligibility and label-type helpers. Positive-stock YourFinds unique items with a barcode and size remain eligible unless returned, preserving existing rules. The picker uses one numeric collator per sort and small, lazy-decoded thumbnails.

The compact inventory snapshot omits delivery metadata. The local label picker joins each record to item details for the same account and inventory revision before reading its delivery ID. Completing background preparation therefore preserves delivery IDs and dropdown choices instead of replacing them with blanks.

Before detail preparation finishes, the picker reuses a revision-keyed browser result or requests a lightweight fallback. That endpoint reads only raw label fields, displayed barcodes and delivery IDs instead of loading full inventory details, Product Master and all date fields. Closing and reopening no longer starts another request while the same cached result remains valid. Failed reads are retryable, and a read invalidated during loading restarts against current data rather than leaving controls locked.

Incremental inventory changes invalidate the fallback result and update an open, idle picker from the current dataset while preserving filters and eligible selections. Logout and full-refresh fallback clear the cached result. PDF generation bypasses the display cache for eligibility checks and still validates selected items against current sheet data; this change targets opening the picker, not PDF conversion time.

## Loading and stock display

Only the first inventory load in a session replaces everything below the header with a loading indicator and disables header actions. Before background preparation completes, uncached queries show loading only in the table. Once the dataset is complete, local filtering and pagination do not show a loader. Text search stays server-backed until detail preparation completes. Background refresh does not hide the table. A hard reload starts the initial loading behavior again.

Cards and their detail dialogs include only records matching every active filter, exclusion and search term. Each product/size group sums only those matching records, so filtering or searching for Incomplete does not include completed stock in the same size. Cards count positive units from matching records; inventory and summary rows preserve their signed stock balances. A group containing only Incomplete, Reserved, Returned or Converted records keeps that status. Sale-price allocations remain separate rows without duplicating physical stock. Searching a barcode counts only the matching barcode's stock, rather than other items in its group.

Completed unique YourFinds items with zero or negative stock are treated as INACTIVE on reads. INCOMPLETE, RESERVED, RETURNED and CONVERTED keep their own statuses. New sales, reservation completions and exchange replacements also persist INACTIVE when they exhaust unique stock. An administrative note marks automatic disabling. Voids and exchanges restore availability only for automatically disabled items when stock becomes positive; manual status changes clear that marker. Historical records and shared size definitions are retained.

## Filters and search

Status and Stock share one **Filters** checkbox dropdown. Several choices can be checked in each section, and the button shows the total selection count. A match can satisfy any checked Status and any checked Stock choice; no checks in either section means any value. Clear selections clears both sections while preserving category and search. These read-only filter controls are available to inventory viewers.

Active and On Sale start checked for each new login; Inactive starts unchecked, and Stock starts unrestricted. Checking Inactive includes inactive items within the other selected filters. The redundant Exclude section is removed, and the browser explicitly sends an empty exclusion list so no hidden exclusion can override an Inactive selection. The internal `DEACTIVATED` value remains compatible with existing sheet/API values; `INACTIVE` and legacy `DISABLED` filter values normalize to it. Converted and Returned are removed from filter choices; their stored records and history are preserved. Backend requests still accept legacy single values and arrays, including older exclusion parameters.

Dashboard Incomplete shortcuts check Incomplete in the visible Stock section. Changing any inventory filter clears the legacy hidden incomplete-only flag, so clearing the Stock selections does not retain an invisible restriction.

Search combines with selected category, status and stock filters. Each result must match the search and the selected choices in each section. Status words are searchable without selecting their corresponding stock filter: for example, searching `incomplete` finds incomplete items within the current filters. Search matches every space-separated term across names, barcodes, sizes, categories, statuses, stock, prices, dates, delivery IDs and other item-detail values. Cost values are searchable only for roles with manager-view access. Search response caches are separated by this server-verified access level, preventing cost-based matches from leaking between roles.

While details are preparing, server searches build the complete search text from bulk inventory and metadata reads, caching it in bounded chunks. Once detail preparation finishes, the browser uses the same pure search-text builder and matching rules. No partial local search is shown while the detailed index is incomplete.

## Verification and limits

Lint, source syntax/include validation, direct-call permission coverage and diff whitespace checks were run. Automated tests, live UI verification and deployment were skipped as requested. No live speed improvement is claimed. Logs distinguish first-page server/response/render times; the progress indicator exposes background preparation separately.

The first uncached server page still reads the workbook. After downloading, browser memory grows with inventory size because the requested behavior retains every compact record and its item details for the session. Before detail preparation finishes or after a failed batch, an uncached action can still require a server read. Very large inventories may eventually need an indexed database. This change uses the existing Apps Script/Sheets architecture and adds no service or data migration.
